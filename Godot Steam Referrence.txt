Godo offers a variety of networking tools such as the multiplayer synchronization and spawner nodes and the RPC system. But before we can build games using those tools, we will need to let Godo know what library drives the networking or more specifically create a multiplayer pier object and initialize Godo's multiplayer networking API with it. The multiplayer pier can be created by multiple networking libraries. The built-in one being Enet, which we used to set up multiplayer in a previous video.

But in this video, we will focus on creating a multiplayer pier using the Steam SDK, which will be provided by a plug-in called Godo Steam. By the end of this video, you will have a working peer-to-peer networking setup where your friends will be able to join your game through Steam without the need for port forwarding. Networking Script

Let's begin with making a networking class. In our file system, let's add a new script that we'll call networking. Here we will initialize networking, create a function to host a Steam lobby, and connect to players who try to join that lobby. Now, I mentioned that we will be making peer-to-peer connections.

If you don't know what peer-to-peer is, it's where all client instances are connected to one another without the need for a central server. Instead, all clients are connected to a hosting player who also participates in the game. Notice that all clients are only connected to the hosting player, not to each other. So any messages from one player to the others are relayed through the host.

We want to create those connections without port forwarding. Port forwarding opens a port on your network to the internet, allowing others to connect to your system, which comes with security risks. So the alternative is to create those connections through something called a relay network. We can initialize access to it by calling steam.init relay network access in our ready function.

In the project settings, we left embed callbacks unchecked because we will use the process function to run those callbacks ourselves. Simply call steam.run callbacks on every frame. This is required to receive any callbacks from steamworks. Next, we will create the host lobby function for which we will need two new constants. a lobby type and the number of people that can join our lobby, ourselves included.

To create the actual lobby, we call steam.create lobby and include the lobby type and the maximum allowed members. Creating a lobby will emit two signals, lobby created and lobby joint in our ready function. Let's connect callables to those signals. This will produce an error because we have yet to declare those callables, but we'll do so in a moment.

First, let's add the signal host created and the variable pair which will be of type steam multiplayer pair. The lobby created signal is only called on the machine of the host. Declare the connected callable on lobby created and make sure to add the signal parameters that we can find by hovering over the original signal. Then we want to initialize the host that other players can connect to and at the bottom emit the host created signal.

The lobby join signal is called for all players who joined the lobby including ourselves since we directly join our own lobby after creating it. So in the on lobby joint callable when we run this code as the lobby owner which we can check by comparing the lobby owner's steam ID to our own we simply want to ignore the rest of this function. Below that we will create the connection to the lobby owner. Notice that in both functions, we create and assign a Steam multiplayer pair object to multiplayer.multiplayer pair.

This effectively tells God that networking is enabled and we can start using KDO's networking API. Setting server relay to true is to accomplish the peer-to-peer setup I talked about earlier where all clients are only connected to the hosting player and any form of communication is relayed through the host. Back in our ready function, let's attach a callable to the join the requested signal. This signal is called when a player is attempting to join a friend through the Steam overlay.

In the connected callable, we'll simply run steam.join lobby with the provided lobby ID. And that's it for our networking script. Let's create an autoload out of it by going to project settings, then globals. Look for the script in the file system and add it to the list.

This automatically adds the networking script as a note to the top of our scene tree upon running the project and it allows us to access the networking contents

Player Controller

Next up is to create the player controller. I went ahead and created a simple character body 2D scene with a sprite and a collider. For the networking part of the controller, we'll add the multiplayer synchronizer node. When we select it, the replication tab opens.

There we can select properties to be synchronized over the network. We want to synchronize the player position. So add a new property. Select the character body node and select position.

The multiplayer synchronizer node automatically synchronizes the properties configured in the list. The user who has so-called authority over the nodes specified in the root path replicates their state of the listed properties to the other players. It's important to specify and assign which player gets authority over what node for each existing instance the host included. The listed properties have a few extra settings.

The spawn setting when checked directly replicates the current state of the property when it's spawned. If left unchecked, it uses the default value instead. With the replicate setting, we can specify when to replicate a property. Then we'll continue with a new script for our player controller.
